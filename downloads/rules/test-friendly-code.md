# 测试友好代码规则

> 面向使用 AI 编程助手（agent）生成 / 修改 Web 前端代码的开发人员。
> 遵循本规则产出的代码，更易于用 Playwright 等 E2E 测试工具编写稳定、可维护的测试。

## 使用方式

将本文件内容（或其中适用章节）追加到项目根目录的 `CLAUDE.md` 或 `AGENTS.md`。
主流编程 agent 会自动加载该文件，编写代码时遵循其中的约定。

## 一、稳定定位器

1. 关键交互元素（按钮、输入框、下拉、弹窗、列表项、链接等）提供稳定的定位属性：优先 `data-testid`，其次是稳定且唯一的 `id` / `name`。
2. 定位值语义化且长期稳定，例如 `submit-order-btn`、`search-input`、`product-item-{id}`；禁止使用随机生成、带时间戳或自增序号的值。
3. 不得依赖以下不稳定方式定位：
   - 纯文本文案（易随国际化、措辞修改而变）；
   - 纯 CSS 层级 / 索引 / 坐标（易随结构调整而变）；
   - 多个同文案元素并存时的歧义匹配。
4. 新增 / 重构组件时，若移动或重命名了元素，同步更新其定位属性，保证既有测试不失效。

## 二、可断言状态

1. 异步过程提供可等待信号：加载中保留稳定 loading 指示；完成时列表渲染、提示出现、按钮恢复等有明确可见的标志。
2. 操作结果可断言：提交成功 / 失败有稳定的提示元素（toast、校验错误、状态文案），并带有稳定定位符。
3. 列表 / 表格数据就绪后应有可等待信号（如 `aria-busy` 消除、空态 / 占位元素稳定呈现），避免测试在元素出现前抢跑。
4. 文案来源稳定可复现：不动态拼接不可预测的内容，错误信息可稳定复现，便于断言与回归。

## 三、语义化与可访问性

1. 使用语义化标签（`button`、`a`、`input`、`label`、`select`、`dialog` 等），不用 `div + onClick` 模拟可交互元素。
2. 可交互元素必须有可访问名称：按钮有可见且有意义的文本；图标按钮提供 `aria-label`；`placeholder` 不替代 `label`，表单控件用 `label for` / `aria-labelledby` 关联。
3. 弹窗 / 下拉等浮层使用正确的 ARIA 角色（`dialog`、`listbox`、`menu`）并管理焦点，使测试可用 `getByRole` 等标准方式命中。
4. 纯装饰的图标 / 图片设置 `aria-hidden` 或空 `alt`，避免干扰定位。

## 为什么

满足上述约定的代码，让 E2E 测试基于稳定的语义与定位符编写，而非脆弱的文本 / 层级，可显著降低测试的编写成本、维护成本与随机失败率。
